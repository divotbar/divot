# Architecture

## Native application

Swift 6.2+, AppKit, Core Animation, and selective Core Graphics/Core Text. The always-visible bar uses AppKit rather than SwiftUI. SwiftUI is permitted for infrequently opened settings. No WebKit or web runtime in the app. There is no reason to introduce a C/Rust subsystem until profiling identifies a bottleneck.

```text
App coordinator (main thread)
  ├─ Display coordinator → left/right NSPanel per display
  │    └─ BarView → small layer-backed item views
  ├─ Configuration store → validated immutable snapshots (left/right groups)
  ├─ Provider coordinator → background data collection
  │    ├─ clock / battery / network / volume / frontmost app
  │    └─ workspace adapter → snapshots and actions
  └─ Settings + AppKit menus/popovers
```

## Panels and geometry

Borderless nonactivating `NSPanel`s own placement and click behavior. A display gets two segment panels so the notch remains outside every hit region. Panels use global screen coordinates, including negative origins; align rendering to the current backing scale. Geometry comes from `NSScreen`, including its auxiliary top areas. `DivotCore.BarGeometry` is the tested, pure layout boundary; platform reads live in the `DivotAppKit` display adapter.

Choose and validate public window levels and collection behaviors on target OS versions. Panels follow a persistent placement state: the top edge when the native menu bar is hidden, below it when the bar appears, returning to the top when it hides. A top band that a camera housing or another bar occupies is not a native-bar signal, so an undecidable display holds the top edge instead of insetting. Because AppKit's default window constraint parks a panel at the bottom of the camera-housing band (`visibleFrame.maxY`) even while the native bar is hidden, the nonactivating panels override `constrainFrameRect(_:to:)` and keep their level just below the system menu bar, so they may occupy the housing band at the top edge while native menus still draw above them. Fullscreen, other Spaces, system menus, and focus cannot be assumed from a style-mask setting. Never adopt private APIs just to match a competitor's feature. Display transitions are coordinated as a batch to avoid intermediate positions.

## Native menu-bar coexistence

Detecting the native bar, not drawing below it, is the feasibility risk. `NSScreen.visibleFrame` exposes the bar on notch-free displays, but the camera housing masks the same band on notched displays, so geometry alone cannot distinguish a hidden from a revealed bar there. Housing detection takes either public signal — `safeAreaInsets.top` or the auxiliary top areas beside the notch — because the inset can read zero while the housing, and a third-party bar such as a-bar (AeroSpace) sharing that band, is still present. That union is what stops an a-bar-occupied top band from being read as a revealed native bar. The supported detector reports a masked display as indeterminate and holds position; it never hides and never polls. A resolved placement feeds `DivotCore.BarGeometry`, which moves the panels below the native bar and drops the notch gap in that row. See the [feasibility evidence](evidence/0009-native-menu-bar-coexistence.md) for what is proven, what is permission-gated, and the open product decision.

## App shell and display coordinator

`DivotAppKit` holds the platform half. `NSScreenGeometryProvider` reads each display into a pure `ScreenGeometryReading`, `AXSystemMenuBarProbe` is the permission-gated optional signal, and `MenuBarObservationAdapter` joins them into `DisplayReading`s. Visibility on the AX path comes from the menu bar's own frame, not `kAXHiddenAttribute`: an auto-hidden bar still reports `hidden == false` because it is slid above the screen rather than AX-hidden, and its frame sits at a negative `y`, so the on-screen position test is the signal that distinguishes revealed from hidden. The adapter is deliberately conservative: the single system-wide AX sample is only consulted for a masked (notched) display when there is one display, so it can never override a notch-free display's `visibleFrame` or be shared across displays, and missing/zero-area attributes are surfaced as indeterminate. Trust in the derived visibility is an explicit configuration opt-in (`menuBar.trustAccessibilityProbe`, default off), so a shipping build never asserts the hardware-specific heuristic globally; while off, a masked display stays indeterminate and holds the top edge, and a direct pointer observation (`DivotAppKit.TopStripCursorMonitor`, an event-driven mouse-moved monitor with no polling, on by default via `menuBar.moveBelowOnCursorReveal`) fills the reveal/hide instead. The pointer reading is attributed per display and, on a notch-free display, is cross-checked against that display's own `visibleFrame`, so a disagreement is corrected to the geometry. `DisplayCoordinator` feeds those to the pure, per-display `DivotCore.DisplayBarCoordinator` and applies the resulting placement to one pair of panels per display. The executable `divot` target is an accessory app: it has no Dock tile or app menu, and its borderless nonactivating panels refuse key/main status, so it cannot steal focus. Its menu-bar item draws the landing-page mark as a template image (`DivotAppKit.DivotMenuBarMark`), so one asset follows the light and dark menu bar. It never polls — it re-evaluates on the shared OS notification set, the pointer crossing a display's top strip, and a single settle timer. `divot --report` prints one observation pass and exits without moving anything. Physical fullscreen/Spaces/display behavior is not claimed here; see the [app shell evidence](evidence/0003-app-shell.md).

## Rendering

Use a shallow `NSView` hierarchy with cached layer-backed contents. Dirty widgets invalidate their own content. Geometry changes trigger layout; a numeric value changing within a stable slot does not. Cache glyph measurements and images keyed by family, variant, scale, appearance, and content. Prefer native text and controls where they offer correct accessibility and interaction; custom drawing must implement equivalent accessibility elements/actions.

`DivotCore.BarMetrics` is the single source for the bar's compact rhythm: the default row height (32 pt, matched to the ~64 px camera-housing band so the row lines up with the notch), the per-side item gaps (both 8 pt by default, the restored pre-#0054 uniform rhythm, #0060), the fixed 17 pt right-edge inset that keeps the camera-in-use indicator clear (`rightEdgeInset`), the row inset (6 pt), the status and app icon sizes, and the font sizes. `BarGeometry` and `BarContentPolicy` read their default height from it, and the AppKit item views read the rest, so no widget hard-codes its own height, padding, or font. The same type owns the pure width measurement (`itemWidth`/`groupWidth`/`fits`) that guarantees a label is never truncated. Each item is sized to the label cell's own measured width (`fittingSize`), not `intrinsicContentSize`, because the latter omits the cell padding and ellipsizes the tail.

Semantic tokens carry foreground, background, accent, selected, occupied, and error roles so the native default and the four theme families share one drawing path. Changing family or appearance invalidates appearance-dependent caches only. Task 0011 implements this: `DivotCore.ThemeCatalog` pins each family variant to its openly licensed upstream palette with attribution, `DivotCore.ThemeResolver` applies the root accent and `appearance.palette` overrides and derives the chrome roles, and `DivotAppKit.BarTheme` bridges the tokens to `NSColor` (or macOS semantic colors for the native family) while honoring increased contrast and reduced transparency. The bar's flat background, item text/icons, workspace selected/occupied/disabled states, error text, and the keep-awake indicator all draw from the tokens; the app-wide System/Light/Dark override plus an effective-appearance hook restyle existing panels without rebuilding providers. Task 0025 makes the chrome flat: `BarContentView` fills one solid `background` token edge to edge with square corners and no material blur or default border, the selected workspace follows the `chipStyle` chip shape while unselected workspaces stay plain (with `chipStyle` off no workspace draws a background and focus is the title weight), and an optional root `bottomShadow` draws a soft gradient along the bottom edge only.

Core Animation handles brief transitions. No display link when idle. Avoid many translucent overlapping layers. Native material and opaque modes share the same geometry; honor reduce-transparency and reduce-motion preferences. Compare compositor costs before choosing the default material.

## State and concurrency

AppKit and view mutations stay on the main actor. Blocking collection and decoding run on bounded background work. Providers emit small immutable snapshots tagged with generation/revision. Ignore stale completions after disable/reconfiguration; cancellation tears down observers and connections. Coalesce burst updates before applying them. One slow provider must not hold up other widgets.

Provider interfaces separate lifecycle (`start`, `stop`), snapshots, and user actions. Maintain a registry of built-in provider identifiers. Clock wakes at the next minute boundary by default; seconds are optional. Battery/power, network, volume, and front-app changes use system notifications. Battery additionally arms a bounded, fixed-interval re-read for a few seconds after each power-source notification (`DivotCore.BatteryRecheckWindow`), because IOKit can deliver the notification before the charging flag flips; it closes as soon as the state settles (unplugged, charging, or fully charged), so a settled machine does not keep reading and this is not continuous polling. CPU/network graphs require bounded sampling and stop when hidden.

Task 0004 implements this as `DivotCore.WidgetPipeline` (an actor): `WidgetProvider.start` runs off the main thread, the `WidgetStore` accepts an emission only for the item's current generation and only when the content fits the item, changed items are coalesced, and the batch reaches the bar through a `@MainActor` sink. Stopping an item delivers a removal so the bar clears it, and reconfigure compares each provider's activation key so a changed option restarts it while an equivalent activation keeps running. `DivotAppKit` supplies the system readings (IOKit power sources, `NWPathMonitor`, Core Audio property listeners, `NSWorkspace`) behind small reading protocols so the logic is testable with mocks. Keep-awake (task 0018) is one such provider action: the battery item's click toggles a `DivotCore.KeepAwakeController`, which owns the IOKit power assertion behind an injectable `PowerAssertionCreating` seam; the battery provider observes the controller and folds the state into its snapshot, so the cup indicator travels through the normal pipeline and quit releases the assertion. See the [native providers evidence](evidence/0004-native-providers.md).

## Workspace adapters

AeroSpace is the first adapter: use the supported CLI/events exposed by the user's installed version. Prefer a persistent subscription when supported; otherwise configured callbacks trigger bounded refreshes. Yabai is the second adapter behind the same interface (task 0012): documented `-m query` reads, `space --focus`, and signal events mapped onto the shared model. Document capability detection and failure modes. Do not rely on undocumented sockets. User actions can execute the CLI asynchronously with a timeout. Never spawn repeated queries on every render or poll workspace state at frame rate. Native macOS Spaces stays a research question: do not imply that NSWorkspace notifications provide a full native workspace adapter. The task 0013 feasibility report closes that question for now — public APIs expose displays and the active Space's on-screen windows but no Space identity, so native Spaces cannot populate the shared adapter model without private APIs; see the [native Spaces feasibility evidence](evidence/0013-native-spaces-feasibility.md).

The interface and the AeroSpace implementation are in place (task 0005). `DivotCore` owns the manager-agnostic model (`WorkspaceID`, deduplicated `WorkspaceApp` identities, focus/occupancy, monitor attribution), the `WorkspaceAdapting` lifecycle, the documented-CLI parser, the manager-selection policy, the per-monitor/overflow layout rules, and the pure feed state machine. `DivotAppKit` provides the bounded subprocess runner, the persistent `aerospace subscribe` event source with reconnect, the icon inventory, `WorkspaceFeed`, which probes capabilities, reads a snapshot, and refreshes on coalesced events across generations so reconfiguration drops stale work, and `WorkspaceBarView`, which draws the left row — real workspace names with focused/occupied/empty state, optional deduplicated app icons, an overflow control that never crosses the camera housing, and the current program beside them; clicking a chip activates that workspace asynchronously. No manager yields the honest unavailable state and draws no workspace chips; nothing fabricates numbered spaces, and when the window listing cannot be read occupancy is `unknown` rather than `empty`. The row's display options come from the validated `widgets.workspaces` object (task 0006), and removing the `workspaces` item from both groups stops the feed. On-device appearance and interaction are not yet physically validated.

The yabai adapter is the second implementation behind that same interface (task 0012). Its parser reads yabai's documented JSON (`query --spaces`, `--windows`, `--displays`) into the shared model: workspace identity is yabai's own `--label` when set and its mission-control index otherwise, focus/visibility and occupancy come from the space listing, and app identities come from the window listing. yabai reports a `CGDirectDisplayID` rather than an `NSScreen` index, so an injected `WorkspaceDisplayIndexResolving` maps it to Divot's 1-based screen index and per-display filtering never assumes ordering; because yabai reports app names and pids rather than bundle ids, an injected `WorkspaceProcessIdentityResolving` supplies the icon key. yabai exposes no persistent event stream — its documented signals run configured callbacks — so the adapter advertises `supportsSubscription: false` and `supportsCallbacks: true`, and the feed reads a snapshot on launch and refreshes on demand instead of fabricating a stream. `YabaiParser` also maps documented signal events (`space_changed`, `display_changed`, and every other named event) onto the shared `WorkspaceEvent`. The read path and `space --focus` are not among the yabai commands documented as needing System Integrity Protection to be partially disabled, so this adapter requires no scripting addition and no private API; yabai's own Accessibility permission and a running service are still required, and their absence surfaces as the honest unavailable state. Live yabai behavior is fixture-tested only and not yet physically validated.

## Configuration and extensibility

One validated `Codable`-style model serves file reload and settings. It expresses ordered `left` and `right` item groups plus namespaced per-item options, and its defaults fill the first-launch bar so customization never starts from blank. Task 0006 implements it: `DivotCore.ConfigurationParser` validates a version 2 document field-by-field (mirroring the website checker) and migrates version 1 explicitly, `DivotCore.ConfigurationStore` keeps the last good snapshot on error and writes atomically after validating, `DivotAppKit.ConfigurationController` publishes snapshots and watches the file, `DisplayCoordinator.apply(configuration:)` rebuilds panels for a changed group, and the provider pipeline starts only the placed items so a removed item stops collecting. `DivotAppKit.DivotSettingsWindowController` hosts the SwiftUI settings form and the `SMAppService` login-item control. The form's last section has a Quit Divot button that confirms through the shared `divotConfirmation` dialog and then takes the same single `DivotAppKit.QuitCoordinator` path as the app and status item menus: it ends through `NSApplication.terminate`, so `applicationWillTerminate` removes the bar and releases the keep-awake assertion (the coordinator also releases it first, idempotently). Theme family colors and palettes are implemented by the theme milestone (task 0011): the settings form selects the family, variant, material, and accent, shows the resolved accent and upstream source line, and the bar repaints live. The future script protocol accepts data and actions, not HTML or executable UI injected into the process. Scripts are opt-in, explicitly trusted local programs with timeouts, output limits, and cancellation.

## Website

Vue 3 + stable VitePress 1.6.4. A custom landing component and shared bar demo sit alongside statically generated Markdown guides. Local fonts, no external assets, no runtime API. Default docs theme supplies local search, sidebar, heading navigation, code blocks, and appearance controls. Production output is ordinary HTML/CSS/JS; direct deep links must work on the chosen host.
